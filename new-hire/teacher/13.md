## Lab results

Measured 2026-11-24 at commit `a091cc2`. Five trials each (seeds 1 to 5), one module a
trial. Run them again before quoting them.

1. `--pretty --trials 5 --carry planned`: 5 of 5 placed. "planning (wall): mean 382 ms,
   worst 400 ms; fits in lift, pull back and clear: 5 of 5". Wall time depends on the
   machine and on what else it is doing.
2. `--pretty --trials 5 --xy 60 --yaw 6`: 5 of 5 placed, worst 0.10 mm along and
   0.38 mm across. The camera copes with twice the designed offset on these seeds.
   Five seeds is not a guarantee; the finder's crop is sized from the designed
   tolerance (`CropFromPrior` in `src/module_finder.h`), so there is an offset at
   which it must refuse.
3. `--pretty --trials 5 --check --calibration 3,0.15 --check-calibration 1,0.05`: 2 of
   5 placed. Three failed with "blocked in touch glass", the tool stopping 2.4 to
   5.0 mm short, peak torque 1.000 of the limit. The finder's error reached 7.8 mm
   along the glass normal. The check after pickup could not help: it corrects the
   place, and these never gripped.
4. `--pretty --trials 5 --check --calibration 1,0.05 --check-calibration 3,0.15`: 5 of
   5 "placed", 0 refused, 0 implausible, 3 "placement unconfirmed" (the set-down was
   blocked). Worst 5.28 mm along and 4.61 mm across; yaw up to 0.150 degrees. The
   measured grip was off the true one by up to 5.5 mm and the script used it. The
   plausibility test did not fire: its tilt limit is 0.2 degrees
   (`PickPlaceOptions::max_check_tilt`). Only the three blocked set-downs were
   noticed, and only as "unconfirmed".

   The same five seeds at smaller errors of the check camera, for the trend:

   | `--check-calibration` | worst along, mm | worst across, mm | unconfirmed | refused |
   |---|---|---|---|---|
   | none | 0.07 | 0.08 | 0 | 0 |
   | 1,0.05 | 1.74 | 1.39 | 0 | 0 |
   | 2,0.10 | 3.51 | 2.99 | 2 | 0 |
   | 3,0.15 | 5.28 | 4.61 | 3 | 0 |

   The error grows in proportion: once, twice and three times the first row's. Stop
   14 uses this as its worked example.

## Questions to ask

1. *Transfer.* Pick a row of the map and explain both sides to me.
   A good answer covers: what the piece does, not only its name; one thing that
   changes for the engineer.
2. *Explain.* Run 3 failed and run 4 "succeeded". Which worries you more, and why?
   A good answer covers: run 3 stopped with a reason and nothing was placed wrongly;
   run 4 placed modules out of tolerance and reported "placed". A failure the cell
   does not notice goes into the product.
3. *Locate.* Where does the code admit that planning time is not really hidden inside
   the motion?
   A good answer covers: the header comment of `src/pick_place.h` ("Here the simulation
   waits for it"); `CarryReport::fits()`; the `time_budget` in
   `src/motion_planner.h`.
4. *Predict.* The check camera's calibration error doubles. What happens to the worst
   placement error?
   A good answer covers: it doubles (the table above); the error passes straight
   through because one picture cannot see it (`src/held_module_finder.h`, step 2).
5. *Explain.* Why can the plausibility test catch some errors of the check camera and
   not others?
   A good answer covers: a turn across the camera's view tilts the measured module on
   the cups, which the cups do not allow; a turn about the camera's own axis is a yaw,
   which they do. The header comment of `src/pick_place.h`, "The plausibility test".
6. *Pitfall.* A colleague reports "our planner is 30% faster than OMPL". What do you
   ask before believing it?
   A good answer covers: the same problem, box, metric and edge-check spacing? Raw or
   shortened paths? How many plans, which seeds? Queries or milliseconds? Same
   compiler flags? If stuck, point at: `docs/ompl-integration.md`, "What makes a naive
   comparison unfair".
7. *Explain.* Why does it matter that there is "one Eigen in the binary"?
   A good answer covers: two libraries passing Eigen vectors to each other must agree
   on what one is; two versions means two definitions of one type.
8. *Transfer.* Of the nine questions under "What the planner would need", which do
   you think your team would put first? Why?
   There is no right answer here. Listen for reasoning from what they have learnt
   about the real cells, and send them to ask.

## Misconceptions to listen for

- "MoveIt is the competitor." It is a framework; OMPL's planners inside it are the
  comparison. The planner here could also run inside it.
- "Real cells use truth for placement too, from better sensors." There is no truth,
  only more measurements, each with its own calibration.
- "The check after pickup makes calibration unimportant." It moves the dependence from
  one camera to the other.
- "Faster planning means a faster cycle." Only when planning is on the critical path.
  Here it runs beside the lift; the carry's duration is what the cycle pays for.
- Reading the gap list as a criticism. It is the research the student was hired for.

## Questions the student may ask

- *Which gap should be closed first?* The owner's decision; `docs/ompl-integration.md`
  ends with "Decisions for the owner" for the OMPL part. Help them reason, do not
  decide.
- *Why write a planner at all when OMPL exists?* The README and the report give two
  reasons that can be checked: every part can be read, and the margin budget
  (`src/motion_planner.h`) is an argument for soundness in metres that a default OMPL
  setup does not give. Whether that is enough is what the comparison is for.
- *Could the simulation be made less kind?* Yes, piece by piece: a grip that can slip,
  a flexible module, a delay in the command path. Each is a candidate for stop 14.
- *What is ISO 10218?* The safety standard for industrial robots and the cells built
  round them. You know it exists; send them to the team's safety engineer.
